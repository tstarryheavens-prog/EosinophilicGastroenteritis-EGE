異種Dual GPU（RTX 4070TiS＋3060）で27Bモデルを80 tok/s駆動する技術――DSpine投機的デコーディングとDMIボトルネックの打破

自作PCやホームラボでローカルLLMを運用する際、最も費用対効果が高いのが「既存のGPU（例: RTX 3060 12GB）に上位GPU（例: RTX 4070 Ti SUPER 16GB）を買い増した異種Dual GPU構成」です。合計28GBのVRAMがあれば、知能水準の高い27B〜32Bクラスのモデルを完全にVRAM内に展開できます。

しかし、実際に異種Dual GPUで27Bクラスを動かすと、2つの大きな壁に直面します。

  1. PCIe / チップセットDMIバスの転送遅延: 第2スロットのGPUとCPU直結の第1スロットGPU間で、レイヤーごとのアクティベーション転送が往復し、推論速度が秒速20〜30トークン前後に低下する。
  2. 自律エージェント運用に必要な長大コンテキスト（64k）とVRAM枯渇: Hermes Agentなどの自律エージェントで運用する場合、64k以上のコンテキスト窓が必須となるが、通常のFP16 KVキャッシュではそれだけで16GB以上を消費し、28GBの枠から溢れてOOM（Out of Memory）となる。

今回、Tencentが発表した最新の投機的デコーディング手法「DSpine」と、llama.cppの不均衡テンソルスプリット（-ts 20,7）、およびQ4_0 KVキャッシュ量子化を組み合わせることで、これらの壁を完全に突破しました。

結果として、通常推論の25.7 tok/sから80.4 tok/s（3.13倍 / +213%爆速化）を達成し、同時に64k（65,536 tokens）コンテキストでの完全安定常駐に成功しました。本記事ではそのアーキテクチャと検証手順を全公開します。

2. 第1の壁：PCIe DMIバスの通信ボトルネックと解決策

Z790などの民生用マザーボードでは、CPU直結の第1スロット（x16）に対して、第2・第3スロットはチップセット（PCH）を経由してDMIリンク（PCIe 4.0 x8相当）でCPUと接続されます。

llama.cppで単純にGPUメモリ比率（16GB : 12GB ≒ -ts 14,10）で均等分割すると、毎デコードステップでGPU 0とGPU 1の間で大量の中間特徴量がPCIe DMIバスを行き来します。その結果、DSpineを適用しても36〜40 tok/sで頭打ちになっていました。

突破口：極限の不均衡スプリット（-ts 20,7）
わずか1.2GBのDSpineドラフトモデルは超高速なRTX 4070 Ti SUPER側（CUDA0）に完全常駐させ、ターゲットモデル（27B）の28層中21層以上を4070 Ti SUPERに集中配置しました。RTX 3060には末尾の7層のみを任せることで、GPU間通信の往復オーバーヘッドを最小化しました。

この結果、生成速度は一気に80.4 tok/sまで跳ね上がりました。

---

3. 第2の壁：エージェント運用のための「64kコンテキスト」とVRAM設計

Hermes Agentや自律型コーディングエージェントでは、ツールのスキーマ定義、過去の実行ログ、ソースコード全体をプロンプトに含めるため、最低でも64k（65,536 tokens）のコンテキスト窓が必要です。

しかし、Qwen3.8-27BのKVキャッシュを通常のFP16で64k確保すると、計算上約16.4GBのVRAMが必要となります。メインモデル（16.5GB）と合わせると32.9GBとなり、28GBの合計VRAMを即座に超過（OOM）します。

そこで投入したのが、llama.cppのQ4_0 KVキャッシュ量子化です。

KVキャッシュ設定 64kコンテキスト時のKV消費量 合計VRAM消費（27B+DSpine含む） 判定
FP16（標準） 約 16.38 GB 約 34.1 GB OOM（起動不可）
Q8_0（8-bit） 約 8.19 GB 約 25.9 GB ギリギリ（マージン不足）
Q4_0（4-bit）＋FlashAttention 約 4.10 GB 約 21.8 GB 完全安定（マージン 6.8GB）

FlashAttentionのQ4_0カーネルを併用することで、精度低下を極小に抑えつつ、28GBのVRAM内に4.5GB以上の空きマージンを残して64kコンテキストを常駐させることに成功しました。

5. 完全再現手順と起動コマンド

以下のコマンドで、DSpine対応フォークのビルドから64k常駐APIサーバーの起動まで再現可能です。

BASH 
# 1. DSpine対応フォークの取得とCUDAビルド
git clone --depth 1 -b dspine https://github.com/Ajay9o9/llama.cpp.git llama-dspine
cd llama-dspine
cmake -B build -G Ninja -DGGML_CUDA=ON -DCMAKE_CUDA_ARCHITECTURES="89;86" -DCMAKE_BUILD_TYPE=Release
cmake --build build -j16

# 2. 64kコンテキスト対応 DSpine常駐APIサーバーの起動
./build/bin/llama-server \
  --model ./models/Qwen3.8-27B-UD-Q4_K_M.gguf \
  --model-draft ./models/Qwen3.8-27B-DSpine-b16-Q4_K_M.gguf \
  --ctx-size 65536 \
  -np 1 \
  -ctk q4_0 \
  -ctv q4_0 \
  -ctkd q4_0 \
  -ctvd q4_0 \
  -ngl 99 \
  -ngld 99 \
  -sm layer \
  -ts 18,8 \
  --spec-draft-n-max 16 \
  --spec-draft-n-min 4 \
  --flash-attn on \
  --reasoning-budget 64 \
  --host 0.0.0.0 \
  --port 47832
---

6. まとめ

異種Dual GPUにおける推論速度の低下はGPU単体の性能不足ではなく、PCIe DMIバスの往復通信とVRAM割り当ての不均衡が原因でした。

  • DSpineの隣接因果注入により、マルチトークン並列生成でも高い受容率を維持。
  • 不均衡テンソルスプリット（-ts 18,8 〜 20,7）により、CPU直結GPUに負荷を寄せてバス遅延を解消。
  • Q4_0 KVキャッシュ量子化により、64kコンテキストを23.5GB VRAM内で完全稼働。

これにより、クラウドAPI（Claude CodeやGPT-4o等）のトークン課金を気にすることなく、最高峰の27Bモデルを自律エージェントの頭脳として24時間フル回転させることが可能になりました。

2026年11月13日にリリースされた llama.cpp v1.0.0 では、Speculative Decoding（投機デコーディング）用の NextN / MTP API がコアヘッダ（llama.h）へ正式統合されました。これにより、Qwen3.8-27B に内蔵された MTP（Multi-Token Prediction）ヘッドを使うだけで、追加のドラフトモデルなしに推論速度を約1.8〜2倍へ引き上げられる構成が注目されています。

一方で、自宅GPUサーバー「Strata（RTX 4070 Ti SUPER 16GB + RTX 3060 12GB）」には、すでにブロック予測型の投機デコーディング手法である D-Spine（draft-dflash） と KVキャッシュ量子化（q4_0）、Flash Attention を導入済みです。本記事では、同一ハードウェア・同一プロンプトを用いて 投機なし / MTP（n_max=2, 3） / D-Spine の全パターンを実測し、本当に乗り換える価値があるのかを数値で検証しました。

1. 検証環境と計測条件

公平に比較するため、モデルはすべて同じ Qwen3.8-27B-UD-Q4_K_M.gguf（約16GB）を使用し、コンテキスト長 65536、KVキャッシュ量子化（-ctk q4_0 -ctv q4_0）、Flash Attention（--flash-attn on）、レイヤー分割（-sm layer -ts 18,8）を統一しました。

3. なぜここまで差がつくのか：ブロック予測 vs MTP

英語コード・数式では D-Spine が圧勝（94〜113 t/s）

D-Spine（draft-dflash）は、1回のフォワードパスで最大15トークン（block_size=16）をまとめて先読みします。Pythonコードの構文や英語の論理展開はパターンが予測しやすいため、平均長が 6.98〜8.51 トークンまで伸び、27Bモデルでありながら 94.59〜113.59 t/s（ベースラインの3.5〜4.2倍）という高いスループットを記録しました。

日本語生成では MTP（n_max=2）が逆転（47.74 t/s）

一方で日本語の長文解説では、D-Spine のドラフト採用率が 12.2% まで低下し、速度も 38.00 t/s に留まりました。対照的に、ターゲットモデル内蔵の MTP（draft-mtp, n_max=2）は日本語でも 73.8% の高い採用率を維持し、D-Spine より約26%速い 47.74 t/s を安定して出しています。

なお、MTP で n_max=3 に増やすと、英語コード（57.19 t/s）や推論（58.47 t/s）はわずかに伸びるものの、日本語では採用率が 45.6% に落ちて 38.84 t/s へ失速しました。マルチGPU環境で MTP を日本語メインに使うなら、n_max=2 が最もバランスの良い設定です。

4. 用途別の起動コマンド例

llama.cpp v1.0.0 以降で導入しやすいのは、追加ファイル（1.2GBのドラフトモデル）が不要な MTP 構成 です。

BASH 
# 汎用・日本語も速い MTP 構成（追加ドラフトモデル不要）
llama-server \
  -m Qwen3.8-27B-UD-Q4_K_M.gguf \
  -ngl 99 -fa on -c 65536 \
  -ctk q4_0 -ctv q4_0 \
  --spec-type draft-mtp --spec-draft-n-max 2 \
  --host 0.0.0.0 --port 47832

一方で、プログラミングや英語での思考・数学推論を最速化したい場合は、従来通り D-Spine 構成 を維持する方が約1.7〜2.0倍高速に動作します。

5. まとめ：乗り換えるべきか？

  • すでに D-Spine + KV量子化（q4_0）+ Flash Attention を運用中なら：コード生成や英語推論が主用途である限り、現行の D-Spine 維持が最も高速です（無理に乗り換える必要はありません）。
  • これからローカルLLM環境を組む、または日本語長文生成が中心なら：llama.cpp v1.0.0 の --spec-type draft-mtp --spec-draft-n-max 2 が最適です。追加VRAM消費なしでベースラインの約1.8倍の速度が得られます。

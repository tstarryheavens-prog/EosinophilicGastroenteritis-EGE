AIエージェントを使って開発を進める際、「どの実行モードを選べばいいのか」で迷うことは少なくありません。Antigravity環境には、タスクの性質に応じて使い分けられる4つの代表的な協調パターン（Orchestrator・/run-workflow・/swarm・/boost）があります。本記事では、それぞれの仕組みと違い、具体的な使い方例をシンプルに整理しました。

1. 4つのモードの比較早見表

まずは全体像を一目で把握できるよう、制御方法・エージェント間の通信・得意なタスクを一覧表にまとめました。

モード 制御の主役 エージェント間のやり取り 向いているタスク
Orchestrator 単一会話内の高性能モデル メインが指示し、高速モデルが実行 通常の機能開発・設計と実装の反復
/run-workflow Python スクリプト 会話せず、構造化データのみ返す 大量ファイルの並列処理・定型パイプライン
/swarm 対等な複数エージェント 共有ボード上で @メンション 交渉 フロント／バック同時開発・仕様すり合わせ
/boost 深層推論 ＋ 独立検証 仮説構築と別視点の検証を集中実行 高難度の並行バグ・アルゴリズム設計

2. 各モードの仕組みと使い方例

① Orchestrator：高性能モデルが計画し、速いモデルが手を動かす

単一の会話スレッドの中で、推論力の高いメインモデルが全体設計と計画を立て、高速なモデル（Hydrogen など）が実際のコード記述や調査を素早く実行する基本スタイルです。人間が1つのチャット欄で対話しながら進めるため、途中で方針を変えても文脈が途切れにくいのが利点です。

PROMPT 
# 使い方例（通常の指示だけで役割分担が走る）
「認証まわりの設計方針をここで整理したあと、
 各エンドポイントのバリデーション実装とテスト追加は
 高速モデルのサブエージェントに割り振って進めてください」

② /run-workflow：Python が並列処理とパイプラインを厳密制御

Python スクリプトが処理の順序と並列実行を厳密に管理するモードです。サブエージェント同士は自由におしゃべりをせず、決められた形式（構造化されたJSONやオブジェクト）の結果だけをスクリプトに返します。余計な対話コストが発生しないため、大量のファイル処理や多段パイプラインを安定して回せます。

PYTHON 
# /run-workflow のイメージ：全ファイル並列レビュー＆集計
results = parallel_map(
    files,
    lambda f: run_agent(f"Check security issues in {f}. Return JSON only.")
)
high_risk = [r for r in results if r["severity"] == "HIGH"]
save_report("security_summary.json", high_risk)

③ /swarm：対等なエージェントが共有ボードで直接交渉

複数のエージェントが対等な立場で参加し、共有のメッセージボード上でお互いを @メンション しながら、APIスキーマやデータ構造のインターフェースを直接交渉するモードです。フロントエンド担当とバックエンド担当のように、作業を進めながら仕様の擦り合わせが何度も発生する開発に向いています。

PROMPT 
/swarm
api担当・ui担当・test担当の3人でダッシュボード新機能を同時実装して。
api担当は型定義が固まったら @ui担当 にメンションで共有し、
ui担当は画面を組んだら @test担当 に結合テストを依頼すること。

④ /boost：深層推論と独立検証で難題を徹底解決

集中した深層推論に加えて、独立した検証プロセスを組み合わせるモードです。並列数を増やすのではなく、1つの難しい問題に対して思考と検証の密度を高めます。再現条件が複雑な非同期・並行バグや、境界条件の厳しいアルゴリズムを確実に解きたいときに使います。

PROMPT 
/boost
WebSocket の再接続処理とキュー消費が同時に走ったときだけ発生する
デッドロックの原因を特定し、修正案と再現テストを作成してください。

3. 迷ったときの選び方（まとめ）

  • 普段の開発・設計と実装をテンポよく回す → Orchestrator
  • 手順が決まった大量の並列処理・データ集計 → /run-workflow
  • 役割の違う担当同士で仕様を擦り合わせながら並走 → /swarm
  • 難解な並行バグやアルゴリズムを1点突破で解決 → /boost

すべてを同じモードで処理しようとせず、作業の性質に合わせて「会話で回すか・スクリプトで縛るか・ボードで交渉させるか・深掘り検証するか」を切り替えるのが、開発スピードと精度を両立する近道です。

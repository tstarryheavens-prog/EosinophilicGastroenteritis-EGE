ローカルLLMを自宅サーバーで運用する際、常に立ちはだかるのが「VRAM・メモリ容量の壁」です。特にパラメータ数が30B〜70Bを超えるフロンティア級モデルは、量子化を行っても20GB〜40GB以上のメモリを要求するため、家庭向けのGPUや小型APUでは起動すらできずOOM（メモリ不足）でクラッシュするのが通例でした。

今回、PlayStation 5のカスタムAPUと同等構成を持つAMDのマイニング用特殊基板「AMD BC-250（Cyan Skillfish 40CU / 16GB GDDR6）」に、SSD動的ストリーミング純C推論エンジン「Colibri（JustVugg/colibri）」とVulkan 1.4（Mesa RADV）を配備。物理メモリ16GBの制約下で、23.1GBの最新スパースMoEモデル「Qwen3.6-35B-A3B」を完全稼働させ、その実測性能と内部キャッシュ挙動、さらに投機デコーディングによる高速化の限界を徹底検証しました。

1. 検証ハードウェアとColibriのアーキテクチャ

AMD BC-250は、Zen 2（6コア/12スレッド）CPUとRDNA 2アーキテクチャの40 Compute Units（2560ストリームプロセッサ）を1チップに統合したAPUです。メモリは16GBのGDDR6ユニファイド構成で、OSや基本プロセスを除くと利用可能な空きRAMは約13〜14GBにとどまります。

この環境に対し、モデル容量23.1GBのQwen3.6-35B（総パラメータ35B / 1トークンあたりのアクティブパラメータ3B）を投入しました。通常ではロードすら不可能な構成ですが、Colibriは以下の3階層メモリ管理によってこれを克服します。

  • 常駐Dense層（VRAM/RAM固定）: 全トークンで必ず計算されるAttention層や埋め込み行列（約1.4GB）を、Vulkanを通じて40CUのGPU側に常駐配置。
  • ホットExpertキャッシュ（RAM動的保持）: 頻繁に呼び出されるExpert層（約4.2GB）をRAM上に保持し、アクセス頻度に応じてLRU管理。
  • コールドExpertストリーミング（NVMe SSDオンデマンド）: 残りのExpert群をPCIe Gen4 NVMe SSD上に配置し、ルーターが選択した瞬間のみダイレクトに読み込み。
--lang 
# ColibriのセットアップとVulkanエンジンのビルド
git clone https://github.com/JustVugg/colibri.git
cd colibri
make -C c qwen36 ARCH=native VK=1

# Qwen3.6-35B-A3B (23.1GB) のダウンロード
python3 ./c/coli setup --model Kreuzzelg/qwen36-35b-a3b-colibri-i4-gs64

# Vulkan 1.4環境でのバックグラウンド起動
python3 ./c/coli start --background

3. 内部ログ解析：SSD帯域とキャッシュヒット率

推論中のColibri内部ログ（serve.log）を精査したところ、3階層ストリーミングの実態が数値として浮き彫りになりました。

  • NVMe SSDストリーミング帯域: 5.29 〜 5.44 GB/s（PCIe Gen4 NVMeの物理限界に近い速度でコールドExpertを毎トークン連続ロード）
  • VRAM常駐ヒット率: 28.0%（32,927 / 117,440回）
  • CPU RAMキャッシュヒット率: 43.2%（50,792回）
  • NVMe SSDオンデマンド読み出し率: 28.8%（33,825回）
  • 総メモリヒット率（VRAM + RAM）: 71.2%

全体の71.2%のExpert呼び出しがメモリ内で完結しており、どうしてもメモリに収まらない残り28.8%のコールドExpertのみを秒速5GB以上のSSDストリーミングで補うことで、16GBのAPU上で35B MoEをエラーなく完走させています。

4. 高速化の検証：投機デコーディング（Prompt Lookup）の限界と突破口

SSDストリーミング推論における最大のボトルネックは「毎トークン発生するSSDへのI/O往復遅延」です。これを克服するため、Colibriに組み込まれている投機デコーディング機能（Prompt Lookup Drafts 深度5 ＆ Speculative Gate）と高速化ポリシー（--policy experimental-fast）を有効化して追試を行いました。

--lang 
# 投機デコード（Prompt Lookup ＆ Speculative Gate）を有効化して起動
COLI_LOOKUP=1 COLI_LOOKUP_DRAFTS=5 COLI_SPEC_GATE=1 \
  python3 ./c/coli serve \
  --model /home/bc250/colibri-models/qwen36-35b \
  --policy experimental-fast

投機デコード適用前後の比較

  • 日本語解説: 2.26 tok/s → 2.35 tok/s（+4.0% 高速化）
  • アルゴリズム: 1.54 tok/s → 1.51 tok/s（誤差範囲）

ログを検証した結果、プロンプトに含まれる構文や反復文字列の生成時には acceptance 100% (4/4 drafts in 4 verifies) と4トークンを一括確定できている一方、自由な新規文章を生成する場面では文脈内に一致するn-gramが存在せず、投機がスキップ（declined）されて通常の1トークン処理に戻っていました。

この結果から、受動的なPrompt Lookupではなく、次のトークンをニューラルネットで能動予測する「MTP（Multi-Token Prediction）ヘッド」の導入、あるいは「IQ3等の3-bit超低ビット化による完全オンメモリ化」が、さらなる倍速化（5〜10 tok/s以上）への本命アプローチであることが実証されました。

5. 結論と運用の展望

AMD BC-250でのColibri実機検証は、以下の明確な知見をもたらしました。

  1. 小規模ハードウェアの常識を覆す容量突破: 16GB機であっても、純Cストリーミングエンジンを用いることで23GB超級の最新MoEをクラッシュなしに常駐運用できる。
  2. 適材適所のノード運用: リアルタイム対話はStrata（RTX 4070TiS, 45〜80 tok/s）に任せ、BC-250は「知能密度の高い35Bモデルによる夜間バッチ、自律エージェントの検証、長文ドラフト」を完全無料・ゼロクォータで回すセカンドオピニオンノードとして極めて実用的である。

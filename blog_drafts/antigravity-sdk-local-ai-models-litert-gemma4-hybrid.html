2026年9月23日、Google Developers Blogにて、Python向けエージェント開発キット「Antigravity SDK（google-antigravity）」がローカルAIモデルに公式対応したことが発表されました。インターネット接続やクラウドのAPIキーを使わずに、手元のPCやローカルGPUサーバー上で自律型AIエージェントを動かせるようになります。

本記事では、この機能がどのような仕組みで動くのか、具体的な導入手順（LiteRT版とOllama等のOpenAI互換サーバー版）、そしてすでに自宅GPUサーバーやHermes Agent等でローカルLLM環境を運用している場合に「何がメリットで、どう使い分けるべきか」を整理して解説します。

一次出典：Introducing Support for Local AI Models in the Antigravity SDK（Google Developers Blog）

1. どんな機能？2つのローカル実行方式

これまでAntigravity SDKで自律エージェント（ファイル読み書き、シェル実行、テスト検証など）を動かすには、クラウドのGemini APIへの接続が前提でした。今回のアップデートにより、バックエンドをローカルモデルに差し替えられる2つの設定クラスが追加されています。

設定クラス 接続先・ランタイム APIキー 特徴と主な用途
LiteRTAgentConfig Google AI Edge LiteRT-LM（.litertlm形式） 不要 Apple Silicon（Metal）やNVIDIA GPU（CUDA）、NPUを自動検出し、SDK側でローカル推論サーバーの起動から終了までを自動管理。Mac単体・完全オフライン環境に最適。
LocalOpenAIAgentConfig 外部のOpenAI互換サーバー（Ollama / LM Studio / vLLM等） 不要 すでに稼働しているローカル推論サーバーやLAN内のGPUマシンにbase_urlで接続。既存の推論環境をそのままエージェントの頭脳として再利用可能。

推奨スペックとして、公式ブログでは最適化されたGemma 4 26B A4Bを動かす場合に「VRAMまたはユニファイドメモリ 24GB以上」を推奨しています。

2. なぜ注目されているのか？3つの技術的メリット

単に「ローカルLLMへテキストを投げる」だけであれば、既存のAPIクライアントでも実現できます。Antigravity SDKならではの強みは、ローカルモデルでも自律エージェントを安定して完走させるためのハーネス（制御基盤）が最初から組み込まれている点にあります。

① ローカルモデル専用の軽量化と自動コンテキスト圧縮

8B〜30Bクラスのローカルモデルは、クラウドの大型モデルと同じ長大なシステムプロンプトや大量のツール定義を渡すと、判断精度が落ちたりKVキャッシュが溢れたりしがちです。

Antigravity SDKの.lightweight()プリセット（LiteRTAgentConfigでは自動適用）を使うと、以下の最適化が自動で行われます。

  • プロンプトの冗長な記述を削減し、ローカルモデルでも指示を見失いにくくする。
  • 標準ツールをコアな開発操作（view / edit / write / bash / list_dir / grep）に絞り込む。
  • LiteRTの64k KVキャッシュ容量に合わせ、40,960トークン到達時点で会話履歴を自動圧縮（Compaction）する。

② クラウド × ローカルのハイブリッド設計をPythonで直書きできる

Googleが公式ブログで特に強調しているのが「Architect-Builder パターン」です。

たとえば、クラウド側のモデル（Gemini 3.8 Flash等）には「ファイル名と課題概要」だけを渡して全体の修正計画を立てさせます（ブログ内の実測例ではクラウド消費わずか95トークン）。実際のソースコードの読み込み、バグ再現、パッチ作成、回帰テストのループは、ローカルのGemma 4 26B群がすべて引き受けます。

この構成により、社外秘のソースコードを外部に一切送信せず、全トークンの97.2%をローカルで無料処理しながら、計画の賢さだけはクラウドの恩恵を受けるというパイプラインをPythonコード1本で組めます。

③ サーバー管理不要のオンデバイス実行（LiteRT）

LiteRTAgentConfigでは、あらかじめ別のターミナルで推論サーバーを立ち上げておく必要がありません。async with Agent(config) as agent:が実行された瞬間に裏側でループバックサーバーが起動し、処理が終われば自動で閉じます。投機的デコーディング（enable_speculative_decoding=True）による生成高速化にも対応しています。

3. 導入手順とサンプルコード

パターンA：LiteRT（Gemma 4 26B）をオンデバイスで動かす

Pythonの仮想環境を作成し、SDKとlitert-lmをインストールした上で、Hugging Faceから.litertlmモデルを取得します（約16.8GB）。

BASH 
python3 -m venv .venv
source .venv/bin/activate
pip install google-antigravity litert-lm

litert-lm import \
  --from-huggingface-repo=litert-community/gemma-4-26B-A4B-it-litert-lm \
  gemma-4-26B-A4B-it-gpu.litertlm \
  gemma4-26b

モデルの準備ができたら、以下のPythonスクリプトで自律エージェントを起動できます。

PYTHON 
import asyncio
import os
from google.antigravity import Agent, LiteRTAgentConfig
from google.antigravity.hooks import policy

MODEL_PATH = os.path.expanduser("~/.litert-lm/models/gemma4-26b/model.litertlm")
WORKING_DIR = os.path.expanduser("~/agy-test")
os.makedirs(WORKING_DIR, exist_ok=True)

async def main():
    config = LiteRTAgentConfig(
        model_path=MODEL_PATH,
        workspaces=[WORKING_DIR],
        policies=[policy.allow_all()],
    ).lightweight()

    async with Agent(config=config) as agent:
        response = await agent.chat(
            "CPUとメモリ使用率を表示する監視スクリプト monitor.py を作り、動作確認してください。"
        )
        async for token in response:
            print(token, end="", flush=True)
        print()

if __name__ == "__main__":
    asyncio.run(main())

パターンB：Ollamaや自宅GPUサーバーに繋ぐ（LocalOpenAIAgentConfig）

すでにOllama、LM Studio、vLLMなどのOpenAI互換APIサーバーが動いている場合は、モデルの再ダウンロードは不要です。LocalOpenAIAgentConfigにmodelとbase_urlを渡し、明示的に.lightweight()を呼ぶだけで接続できます。

PYTHON 
import asyncio
from google.antigravity import Agent, LocalOpenAIAgentConfig

async def main():
    # Ollama や vLLM、自宅GPUサーバー等の OpenAI 互換エンドポイントに接続
    config = LocalOpenAIAgentConfig(
        model="gemma4:26b",
        base_url="http://localhost:11434/v1",
    ).lightweight()

    async with Agent(config=config) as agent:
        response = await agent.chat("このディレクトリの構成と主要ファイルを要約してください。")
        print(await response.text())

if __name__ == "__main__":
    asyncio.run(main())

※ litert-lm serveで立てたサーバーにLocalOpenAIAgentConfigで繋ぐのではなく、LiteRTを使う場合はLiteRTAgentConfigを直接指定する仕様になっています。

4. 既存の「自宅GPUクラスタ × Hermes Agent」構成と比較してどうなのか？

すでに自宅に推論用GPUサーバー（Ollama / vLLM / llama.cpp等）を立て、Hermes Agentや自作のモデルルーターでローカルLLMを運用している場合、Antigravity SDKは競合するのか、それとも併用できるのかを整理します。

比較項目 既存の自宅GPU ＋ Hermes Agent構成 Google Antigravity SDK（ローカル対応）
バックエンド共有 OpenAI互換API（/v1）を共有できるため、同じGPUサーバーを両方から同時に利用可能。（※ .litertlmファイルだけは専用形式のため共有不可）
推論速度とメモリ負荷 常時稼働の専用GPUサーバー側で処理するため、手元のMacのメモリを圧迫せず高速。 LiteRTAgentConfigは手元PCのメモリを24GB以上消費。ただしLocalOpenAIAgentConfigなら外部GPUサーバーを使える。
普段使いのエージェント チャットUI、永続メモリ、タスク管理、Cron、ACP連携などが最初から揃っており強力。 あくまでPythonプログラムに組み込むSDK部品。UIや常駐管理は自前で組む必要がある。
スクリプト単位の自動化 単発のAPI呼び出しルーターと、高機能なHermes本体の中間領域はやや手間がかかる。 Python数十行で「ファイル編集・bash実行・テスト検証」の自律ループを軽量に量産でき、policiesで権限も厳密に制限可能。

結論：置き換えではなく「軽量ワーカー部品」としての併用が最適

日常の対話やマルチエージェント運用、スケジュール実行といった基盤は、すでに完成しているHermes Agentや自宅GPUクラスタをそのまま使い続ける方が高機能で快適です。

その上で、Antigravity SDKのローカル対応が活きるのは次の2つの場面です。

  1. 特定の自動化バッチをPythonで切り出したいとき: LocalOpenAIAgentConfigの接続先に自宅のGPUサーバーを指定すれば、「夜間テストを実行し、失敗したらパッチを書いて再テストする」といった専用ワーカーを数十行のコードで安全に量産できます。
  2. 外出先・完全オフラインでMac単体作業をしたいとき: 自宅サーバーへVPN接続できない環境でも、LiteRTAgentConfigを入れておけばMac単体でコード修正やスクリプト生成を完結できます。

5. まとめ

Antigravity SDKのローカルモデル公式対応は、クラウドAIの設計力とローカルAIのコスト・機密性を1つのコードベースで両立させる実践的なアップデートです。

  • オフライン単体運用ならLiteRTAgentConfig（Gemma 4 26B）
  • 既存のOllamaや自宅GPUサーバーを活かすならLocalOpenAIAgentConfig
  • コード実行時は.lightweight()でプロンプト軽量化と自動圧縮を有効にする

既存のHermes AgentやGPUサーバー資産を壊すことなく、用途に応じてPythonスクリプトから手軽にローカル自律エージェントを呼び出せる選択肢として、ぜひ押さえておきたい機能です。
